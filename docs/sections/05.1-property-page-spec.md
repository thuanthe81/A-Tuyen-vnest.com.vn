## 4. Checkpoint 1 as built

**Route.** `/stays/[property]` is generated ahead of time for every property the repository serves. The server never reads dates or guests, so the page is identical for every guest and has one canonical address. An unknown property is a 404.

**Stay in the URL.** The booking bar and the room selection read the stay in the browser (`useStayFromUrl`), each inside its own Suspense boundary with a placeholder of the same size. Availability loads by itself and cannot delay or change the property content.

**Legacy address.** `/stays?property=<slug>` redirects (307) to `/stays/<slug>`, carrying only dates and guests that parse. The frozen booking bar is unchanged: it still submits there and the site forwards the guest. An unknown property stays on `/stays`.

**Shell.** One picture where the gallery will be (the first of the record's gallery, or its signature visual); area, name and one line; "Xem phòng trống", a plain link to the rooms on the same page that keeps the stay in the URL and works before any script loads; then the existing room selection. Amenities and nearby are not built and nothing stands in for them.

**Shared answer.** `src/app/stays/layout.tsx` keeps the last availability answer above both routes, so going from results to a property makes no second request.

**Content fields** (optional, validated): `identity.galleryMediaIds`, `Amenity.icon` (a fixed list, `AMENITY_ICONS`), `RoomType.highlight`. See `docs/CONTENT_MODEL.md`.

## 5. Acceptance criteria for the section

**Structure and SEO**

- [x] Property content is in the first HTML response and does not depend on dates.
- [x] Canonical is the address without parameters, identical with and without dates.
- [x] A sample or draft property is `noindex`; only a real, approved one on an indexable deployment is indexable.
- [x] Structured data is emitted only for a real, approved property, and never states price, availability or rating.
- [x] `/stays?property=` redirects with valid criteria preserved; nothing unparsed reaches the address.
- [ ] Verified with a real, approved property record (none exists yet).

**Booking access**

- [x] "Xem phòng trống" is within the first screen at 390px and jumps to the rooms with the stay kept.
- [x] Before a rate is chosen, the only pinned element is the criteria bar.
- [x] Results to property makes no second availability request.

**Gallery, amenities, nearby** (later checkpoints)

- [ ] At most five visible pictures with "+N"; only the primary picture loads with high priority.
- [ ] Swipeable on a phone without a library; usable by keyboard; captions and alt text from the record.
- [ ] Amenities show an icon only when the record names one; nearby shows distance or time only when the record has it; both hide when empty.

**Quality**

- [x] 390, 768 and 1440px: no horizontal overflow (shell).
- [x] Layout shift below 0.1 in tested transitions (shell: 0).
- [ ] Added JavaScript within 20 KB gzip per route. **Not met at checkpoint 1**: see below.
- [x] Lint, typecheck, tests and build pass.

## 7. Known limitations

- The gallery is one picture; amenities and nearby are absent.
- The room selection is the interim presentation from section 02.2.
- Stay rules from the provider (minimum nights and similar) are not known to the static page; the availability endpoint still applies them and its answer is shown.
- A search from the property page goes through the legacy address and one redirect, because the frozen bar builds that address.
- Nothing has been checked against real VNest content or photography.
