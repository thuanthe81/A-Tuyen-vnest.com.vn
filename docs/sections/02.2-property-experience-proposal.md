# 02.2 redirection: visual-first property experience (design proposal)

**Status: ARCHITECTURE APPROVED by the owner, 11/10/2026**, with refinements: at most five gallery pictures with "+N"; the three content fields; a provisional 20 KB script budget per route; the property page recorded as section 05.1. Built checkpoint by checkpoint; progress is in `05.1-property-page-spec.md`.

Principle set by the owner: **Visual First. Details on Demand. Booking Without Friction.**

Statements about guests or conversion are **hypotheses**. Every example name, amenity, place and price below is a placeholder; none describes a VNest property.

## 1. Revised information architecture

| Address | What it is | Guest's question | Indexing |
|---|---|---|---|
| `/stays` | Multi-property discovery. With dates: search results (today's Journey A, kept) | "Where should I stay?" | `noindex` with any parameter. Bare address: see the directory proposal in the 02.2 draft record |
| `/stays/[property]` | **New.** The property: gallery, identity, amenities, nearby, room selection | "Is this the place, and which room?" | Indexable for a real, approved property. Canonical has no parameters |
| `/stays?property=x&…` | No longer a page | | Redirects to `/stays/x` with the same dates and guests |
| `/api/availability` | Unchanged | | Never indexed, never cached |

**How a guest arrives at a property page**

1. From results: "Xem phòng" on a card links to `/stays/[property]` with the dates.
2. From the booking bar with a property chosen: the frozen bar still submits to `/stays?property=…`; the server redirects. Section 02.1 is not changed.
3. From a search engine or a shared link, with no dates: the page is complete as content; rooms are listed without prices until dates are chosen.

**Order of the property page**

1. Booking criteria (compact bar, always in reach)
2. Gallery
3. Identity: name, area, "Xem phòng trống"
4. Amenities
5. Nearby
6. Rooms

Search criteria travel in the URL on every link, as they do now (`routes.property(slug, locale, criteria)` already exists).

## 3. Component breakdown

| Component | New or reused | Rendered | Notes |
|---|---|---|---|
| `app/stays/[property]/page.tsx` | New | Server, static per property | Reads the record only. Does not read dates, so it can be generated ahead of time |
| `app/stays/layout.tsx` | New | Server + one client provider | Holds the availability answer above both routes, so results → property still needs no second request |
| `PropertyGallery` | New | Server markup, CSS only | Grid from 768px; scroll-snap strip below. No carousel library, no script for swiping. Uses `CardVisual` |
| `PropertyIdentity` | New, small | Server | Area, name, optional one line, the anchor action |
| `AmenityIcons` | New | Server | Icon and label. About twelve inline icons, one generic fallback |
| `NearbyExperiences` | New | Server | Grouped by the record's existing categories. Renders nothing when the record has none |
| `RoomSelection` | **Reworked from `PropertyRooms`** | Client | Same rules, same states, same selection logic; new collapsed presentation |
| `RoomBlock`, `RateList`, `TermsDisclosure` | New presentation | Client | Native `<details>` or a labelled button for disclosure |
| `SelectionSummary` | Extracted from `PropertyRooms` | Client | Now also shows the chosen rate's full terms |
| `useAvailability`, `derive.ts`, `PriceLine`, `PriceUnavailable`, `StatusLabel`, `Notice` | Reused unchanged | | All tests kept |
| `ResultsSearchBar` (frozen 02.1 bar inside) | Reused unchanged | Client | |
| `PropertyCard`, `AllPropertiesResults` | Reused; one link changes | | "Xem phòng" points at the property page |

**Content model additions** (all optional, additive, in `domain/property.ts`, covered by the content gate):

| Field | Why |
|---|---|
| `identity.galleryMediaIds` | The ordered pictures for the hero. Without it the hero shows the signature image alone |
| `Amenity.icon` | A key from a fixed list. Without it the generic mark is used; an icon is never guessed from a label |
| `RoomType.highlight` | The "one meaningful distinguishing characteristic", in VNest's words. Fallback order when absent: bedding, then capacity, then area, then nothing |

Nearby experiences need no change: the record already has a category, and optional distance and travel time that are shown only when present.

Video: `VideoAsset` with a required poster already exists. The gallery accepts media ids, so a video can take the primary slot later; this proposal renders its poster only.

## 4. Effect on section 02.2 and on Phase 05

**What is kept from 02.2 as built:** the availability contract, the mock scenarios and fixtures, `useAvailability`, every rule in `derive.ts`, the five states, stale handling, retry, the missing-price rules, Journey A, the shared card, all 160 unit tests.

**What is replaced:** the Journey B screen (`PropertyRooms` as a page inside `/stays`). Its logic moves into `RoomSelection`; its tall cards go.

**Overlap with Phase 05 (property detail pilot).** `/stays/[property]` is the address Phase 05 was going to build. This proposal takes its booking-critical slice early. A proposed split, for the owner to confirm:

| Now, under this proposal | Left for Phase 05 |
|---|---|
| The route, its metadata and structured data | Per-property layout templates (`presentation.layout`) |
| Gallery hero | Long-form story sections (`presentation.sections`) |
| Identity strip | Per-property theme tokens |
| Amenity icons (top set) | Full amenity list, policies, FAQs |
| Nearby, compact | Map, richer local guide |
| Room selection | Room detail pages (`/stays/[property]/rooms/[room]`), full-screen gallery viewer |

Everything on the left is built as shared components that a Phase 05 layout places, so Phase 05 extends this page instead of replacing it.

**Numbering.** Recommended: keep 02.2 as "search results and room selection", and record the property page shell as a new section **05.1, "property page: booking slice"**, authorised early. The alternative, keeping it all inside 02.2, makes one very large section that is hard to approve and freeze.

## 5. SEO and booking-state implications

**SEO**

| Topic | Proposal |
|---|---|
| Rendering | Property content is in the first HTML response, generated ahead of time per property. Availability is added in the browser |
| Dates in the URL | The server does not read them, so the page stays static and cacheable. The booking bar and room selection read them in the browser |
| Canonical | `/stays/[property]`, no parameters, whatever dates the URL carries |
| Indexing | Only for a property that is real and approved (`isPublishable`) on an indexable deployment. Fixtures are always `noindex` |
| Structured data | The existing lodging and breadcrumb builders, which already refuse sample records and never emit price, availability or rating |
| Sitemap | Already lists publishable properties at this address |
| Redirect | `/stays?property=x` → `/stays/x`, temporary (307) while URL words are still provisional |
| Images | Real alt text from the record; one eager image; explicit dimensions |
| Still open | The public URL word (`stays`) and slug language, to be settled before launch |

**Booking states**

| State | Collapsed room block | Elsewhere |
|---|---|---|
| Verified rate | "từ" lowest verified total, nights, short tax label, "Chọn" | Full terms in the opened block and in the summary |
| No verified price | "Chưa có giá"; no figure. Selectable as a room only if the provider declares a hand-off | Unchanged rule from the last pass |
| Sold out | Muted row, "Hết phòng", listed after the others | If every room is sold out: a notice with "same dates, other properties" |
| Over capacity | Muted row, "Tối đa N khách" | "Đổi số khách" |
| Provider error | No rows claim anything | Notice above the rooms with "Thử lại". Never shown as sold out |
| Stale | Prices quietened, "Kết quả cũ" | Notice with "Cập nhật giá"; continue disabled |
| No dates | Rooms listed with their trait, no price | "Chọn ngày" opens the booking bar |
| Loading | Outlines the size of the final blocks | Gallery, amenities and nearby are already on screen: they do not depend on the provider |

One consequence worth stating: because the property content is server-rendered and does not wait for availability, the layout-stability problem of the last pass does not return. Only the room list has outlines.

**Material terms before confirmation.** Progressive disclosure must not hide what a guest is agreeing to. The rule proposed: the collapsed block always shows the total and tax status; the opened block shows one line of cancellation terms per rate with the full text one tap away; and the selection summary shows the chosen rate's full cancellation and payment terms, in the provider's words, before the continue action. Final confirmation belongs to section 02.3, which must repeat them.

## 6. Design rationale and trade-offs

| Decision | Reason | Trade-off |
|---|---|---|
| Photography first | The property's character is the product. Hypothesis: for guests choosing a distinctive stay, pictures decide faster than text | The first room moves from the first screen to about two screens down on a phone. Mitigated by a persistent "Xem phòng trống" action and the sticky criteria bar. **This reverses an acceptance criterion of the original 02.2 specification** and should be accepted knowingly |
| A property page, not a panel in results | Content that belongs to a property needs its own address to be indexed, shared and linked | Pulls part of Phase 05 forward |
| Collapsed room blocks | Six to ten rooms become scannable in one screen instead of several | Terms are one tap away. Mitigated by the summary rule above |
| Icons with labels, never icons alone | Recognition without relying on a picture's meaning | Needs an icon key per amenity from VNest's content; a generic mark until then |
| Nearby as categories | Scannable; no map dependency | Thin until VNest supplies verified places. The section hides itself when empty |
| CSS scroll-snap gallery | No library, no script, works with a keyboard and a screen reader as a list of images | No autoplay, no zoom viewer yet (left for Phase 05) |
| Mock imagery | Real photography is not available | The emotional effect cannot be judged on drawn stand-ins. Structure, proportion and behaviour can |

Other effects:

- **JavaScript.** Splitting the journeys by route means `/stays` no longer loads room-selection code and the property page no longer loads results code. Expected to bring each route under the requested 20 KB; to be measured, not assumed.
- **Fixtures.** Each mock property needs four to six labelled gallery pictures and a few labelled nearby entries and icon keys. All drawn, all marked "ẢNH MẪU".
- **What cannot be claimed.** Nothing in this direction has been tested with users. "Younger travellers prefer visual-first" stays a hypothesis.

## 7. Proposed implementation sequence

Each step ends with tests passing and can be reviewed alone.

1. **Content model.** Add the three optional fields and their validation; extend the six fixtures with labelled gallery pictures, icon keys and nearby entries.
2. **Route and redirect.** `/stays/[property]` rendering identity only; `/stays?property=x` redirects; result cards link to it; availability provider moved to a shared layout. Verify results → property still makes no second request.
3. **Gallery.** Desktop grid and phone swipe, with keyboard and reduced-motion checks.
4. **Amenities and nearby.** Icon set, empty states, no-data behaviour.
5. **Room selection.** Collapsed blocks, disclosure, rate list, summary with full terms. Re-point the existing rendered checks for states, selection, stale and missing price.
6. **SEO.** Metadata, canonical, structured data, static generation; verify in the response of a production build.
7. **QA.** 390, 768, 1440; layout shift; JavaScript per route; section 02.1 regression; keyboard.
8. **Records.** Update the draft decision record and the roadmap; stop for review.

Section 02.1 is not touched in any step. The availability contract is not changed.
