## 1. Section objective

Give a guest one obvious, pleasant way to start a booking from the first screen, and keep it one tap away while they browse. Reusable on the homepage hero, in the sticky navigation and on property pages.

## 2. Approved design and final field structure

**Fields, in order (owner's decision, 10/10/2026):**

| # | Field | Required | Default |
|---|---|---|---|
| 1 | Property ("Cơ sở") | No | "Tất cả cơ sở" (all properties) |
| 2 | Check-in ("Nhận phòng") | Yes | Empty |
| 3 | Check-out ("Trả phòng") | Yes | Empty |
| 4 | Guests ("Khách") | Yes | 2 |
| 5 | Search ("Tìm kiếm") | | |

There is no promotional code field. It was removed by the owner; codes may belong to a later booking stage.

**Visual design: a soft rectangular floating bar.**

| Element | Value |
|---|---|
| Silhouette | 14px corners; 8px fields inside 6px padding, so inner and outer corners stay concentric |
| Surface | Warm matte off-white `#fbf9f5`, solid (no blur) |
| Depth | One hairline plus one low, soft shadow |
| Fields | 60px tall; small uppercase label (11px, 0.12em tracking) over the value (15px, 16px from 1024px) |
| Dividers | 40px hairlines between groups |
| Search button | Copper `#b04f2a`, hover `#9a4526`, white label, 8px corners |
| Panels | 16px corners; calendar days and controls are 8px rounded squares; selection is ink, not copper |

Three presentations of one search:

- **Floating bar** (768px and up), over the lower part of the hero.
- **Compact sticky bar**, fixed to the top after the guest scrolls past the floating bar: same fields as one-line values, icon Search button.
- **Mobile** (under 768px): a two-line bar (where; when and who) that opens a full-screen panel.

**Provisional elements inside the approved design:** the copper (VNest's logo has not been supplied, so the colour is not sampled from it), the typeface (Be Vietnam Pro), and the Vietnamese wording (written by the build team).

## 3. Why the soft rectangle was chosen over the capsule

The first two iterations used a fully rounded capsule. On review the owner found it too close to common hospitality booking patterns, and asked for a more architectural, editorial alternative. Both were built on the same components and compared over the same backdrop; the owner chose the rectangle.

| | Chosen: soft rectangle | Set aside: capsule |
|---|---|---|
| Silhouette | 14px corners | Fully rounded (9999px) |
| Search button | Copper, 8px corners | Ink `#1c1d1f`, pill |
| Depth | Hairline plus low shadow | Contact shadow plus soft ambient shadow |
| Type | Values 15/16px, tracking 0.12em | Values 15px, tracking 0.08em |
| Field height, divider | 60px, 40px | 56px, 28px |
| Days, controls | 8px rounded squares | Circles |
| Panels, list rows | 16px, 8px | 28px, 16px |

Reasons recorded at the time: the rectangle is less common in hospitality; squarer fields give labels and values more room; copper makes Search the only coloured element. Known trade-off: on warm imagery the copper sits close to the background tones.

The capsule's values are listed so it could be restored by changing the `--bk-*` variables alone. Its code was removed so that one design is maintained.

## 4. Why property selection is optional

- A guest who has not chosen among six properties is exactly who a multi-property site most needs to help. Making property mandatory would stop them at the first field.
- "Tất cả cơ sở" is a real option and the default, not a placeholder. The field therefore always shows a complete answer, never looks empty, and can never produce a validation error.
- In state, `propertyId = null` is an explicit value meaning all properties. The state holds the property's stable id; the URL carries its slug; display names are never identifiers.
- An unknown property in a URL falls back to all properties silently.

## 6. Interaction decisions

**Desktop and tablet**

- Each field opens its own panel: a property list, a calendar (two months from 900px, one below), a guest stepper.
- A panel opens above the bar when there is no room below, which is the usual case low on a hero.
- Check-in and check-out are one group because they are one decision. The stay is drawn as a band between two filled days, and previews under the pointer while check-out is being chosen.
- Changing check-in keeps a check-out that is still later, and clears one that is not. It is never moved silently.
- Choosing a property moves focus to check-in; completing the dates moves it to guests. Nothing opens uninvited.
- Search with missing or invalid dates opens the calendar with a text message. Escape and outside click close a panel.
- The weekday is shown from 1024px ("Th 5, 12 thg 11") and dropped below it ("12 thg 11") before anything truncates.

**Sticky**

- An IntersectionObserver on the floating bar decides the hand-over. No scroll listener and no pixel offset, so it is correct whatever the hero's height.
- The sticky bar is `position: fixed`, so it never moves the page, and is inert while hidden.
- It has a slot for the site mark so it shares one row with the header (section 03.1).

**Mobile**

- A row of four fields cannot be made comfortable at 390px, so the phone gets a different interaction, not a squeezed copy.
- The panel opens on the dates, which are required. Property sits above as one collapsed row already reading "Tất cả cơ sở".
- One step is expanded at a time; a finished step collapses to a one-line summary and focus moves to the step that opened.
- Search is fixed at the bottom of the panel. The panel is a native modal dialog.

## 7. SEO and performance

- The bar is a client component inside a server-rendered page; page content does not depend on it.
- The form is in the server HTML with real labels. It does not function until its JavaScript has loaded.
- Search navigates with the client router: no full page reload.
- Criteria and the optional `property` slug live in the query string, which canonical URLs exclude.
- Dates are formatted without `Intl` or `Date`, so server and browser print identical text.

Measured on the production build on a local machine:

| Measure | Result |
|---|---|
| JavaScript added by the feature, gzip | About 9 KB (182 KB route total against 172 KB for a page without it) |
| CSS, gzip | 6 KB for the whole site |
| Layout shift on load and when the sticky bar appears and leaves | 0 |
| Runtime dependencies added | None |
| Console errors | None |

Not measured: Lighthouse, real devices, behaviour over a real hero image or video.

## 8. Component architecture and PMS-independent contracts

```
src/features/booking-search/
  search-form.ts            pure state and rules (tested)
  calendar.ts               pure month grids (tested)
  format.ts  copy.ts  summary.ts
  StaySearchProvider.tsx    the one shared search; builds the destination URL
  BookingBar.tsx            the bar, full and compact
  MobileBookingSearch.tsx   mobile bar and full-screen panel
  HeroBookingBar.tsx        floating bar or mobile bar, and the scroll boundary
  StickyBookingBar.tsx      fixed compact bar with a slot for the site mark
  fields/                   PropertyPicker, DateRangeCalendar, DateFieldTabs, GuestStepper
src/styles/tokens.css       --bk-* variables: shape, depth and Search colour
```

Presentation, state, validation and URL serialisation are separate files. The components hold no booking rules; the rules hold no markup.

**Contracts** (full detail in `docs/BOOKING.md`):

- The bar never calls a provider. It produces a URL: `property` (optional slug), `checkIn`, `checkOut`, `adults`.
- A provider is asked through one request shape for both searches: `scope` (`single-property` or `all-properties`) and an explicit list of property ids. The site resolves "all" to that list.
- `/api/availability` accepts a search with or without a property.
- If a PMS has no multi-property search, its adapter asks once per property and merges the answers. Nothing is assumed about ezCloud or GoHost.

**Shared files extended for this section** (they belong to Phase 01, which is in review and not frozen): calendar arithmetic in `domain/dates.ts`; the `property` filter in `domain/search.ts`; `SearchScope` in `domain/availability.ts`; all-properties search in `server/availability.ts`; `config/routes.ts`, `config/site.ts` (site timezone); `styles/tokens.css`, `styles/fonts.ts`, `app/layout.tsx`; `test/register.mjs`.

## 9. Alternatives considered

| Alternative | Why not chosen |
|---|---|
| Fully rounded capsule | Set aside by the owner as too familiar (section 3) |
| Flat bar integrated under the hero | Owner's direction was a floating bar |
| Promotional code in the search | Removed by the owner; a code cannot be verified at search time |
| Property as a required first step | Blocks undecided guests (section 4) |
| Native `<select>` for property | Cannot show the area beside each name or match the bar; the radio list keeps native keyboard behaviour |
| Native date inputs | No range in one gesture; inconsistent across browsers; cannot be styled |
| A date-picker library | A dependency about the size of the whole feature |
| Stacking the fields on phones | Covers the image the hero exists to show; cramped at 390px |
| Partial-height bottom sheet on phones | A calendar needs the height; forces a scroll inside a scroll |
| Scroll listener with a pixel threshold | Breaks when the hero's height changes |
| Sending a single-property search straight to the property page | Property pages do not exist yet. Open for 02.2 |

| Automated tests | 122 of 122 pass | |

Limitations:

- **Not tested:** real phones (on-screen keyboard, safe areas, momentum scrolling), screen readers, browsers other than Chromium, real users.
- **No component or end-to-end tests.** Rules are unit-tested; interactions were verified by hand and by scripted checks in one browser.
- **Sample data only.** The property list shows three neutral sample properties, not VNest's six. Long real names are untested; the field truncates with an ellipsis.
- **Not compared side by side with the reference screenshot or the PDF**, which never reached the working session.
- **Drawn backdrop.** Not judged over real imagery or video. On warm imagery the copper is close to the background tones.
- **The bar does nothing until its JavaScript has loaded.**
- **Provisional:** copper, typeface, Vietnamese wording, and the assumption that all properties share the `Asia/Ho_Chi_Minh` timezone.

Future integration requirements:

- Real property options from the content repository (`id`, `slug`, `name`, `area`) for the six properties.
- Verified stay rules from the provider, if any (minimum and maximum nights, maximum guests). None are invented; guests are capped only at the parsing ceiling of 99.
- For 02.2: whether a single-property search lands on results or on the property page; how partial failure across properties is reported.
- For 03.1: the sticky bar needs a slot on its right as well as its left. That is a change to this section and requires approval once it is frozen.
- Not built, to add only if required: children, number of rooms, promotional codes.
